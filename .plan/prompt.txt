# 项目目标

请从零构建一个可维护、可扩展、支持大规模并行处理的 Python 项目，用于从海量医学科研文献中自动抽取结构化知识，并持续构建一个可追溯、可增量更新的医学知识基座。

本项目不是简单的 demo，也不要直接 fork 或复制已有知识图谱项目。需要根据以下业务目标自行设计代码，同时参考成熟开源项目的优秀架构。

## 一、参考项目与借鉴原则

主要参考仓库：

`mims-harvard/OptimusKG`

重点借鉴其：

* Landing → Bronze → Silver → Gold 的分层数据流水线思想；
* 将原始数据、抽取结果、规范化数据、最终知识库解耦的方式；
* pipeline node 尽可能设计为输入明确、输出明确、可独立执行和测试的函数；
* 配置与业务代码分离；
* 中间结果持久化，从而支持失败恢复、局部重跑和可复现构建；
* 面向大规模数据的并行执行思想；
* provenance、数据来源和中间数据可追踪设计。

不需要照搬 OptimusKG 的具体数据源、BioCypher、Kedro 或 Neo4j 实现；如果使用更简单的 Python 架构能够达到同样目的，应优先保持项目简单和可维护。

关系抽取与规范化流程可参考 EDC（Extract → Define → Canonicalize）的思想：

1. 首先进行开放式知识抽取；
2. 保存 LLM 给出的原始细粒度关系；
3. 再将关系映射到一个较稳定的 canonical relation vocabulary；
4. 无法可靠映射的关系不得强制归类，应保留原始关系。

---

# 二、核心输入

输入是一批已经存储在本地的医学论文文本。

不负责在线下载论文。

假定每篇论文已经能够被读取为完整文本，并具有稳定的：

* `document_id`
* 文件路径
* 标题（若存在）
* DOI / PMID 等来源标识（若存在）
* 文本正文

主要语料覆盖：

**糖尿病及其相关医学、生物学、人体健康和生活方式研究。**

但是知识抽取范围不能限制在糖尿病本身。

只要论文中出现具有医学、生物学、人体、生理、病理、药理、分子、遗传、营养、环境、生活方式或临床意义的知识，都应该允许抽取。

---

# 三、全文处理原则

禁止默认将论文切成 chunk 后独立抽取。

每一次知识抽取 LLM 请求都应能够看到完整论文正文，从而保留：

* 跨段落信息；
* 跨章节关系；
* 指代信息；
* 实验整体背景；
* study design；
* population context；
* 前后文限定条件。

系统应针对现代 long-context LLM API 设计。

但是“全文输入”不代表一篇论文只能调用一次 LLM。

为了提高 recall，可以针对同一篇完整论文进行多个 extraction pass，例如：

1. entity inventory；
2. disease / phenotype relations；
3. drug / treatment relations；
4. gene / protein / pathway relations；
5. physiological / biochemical relations；
6. risk factor / lifestyle / environmental relations；
7. population / clinical outcome relations。

每个 pass 均允许看到完整论文。

多 pass 应设计成可配置功能；第一版可以从较少 pass 开始。

---

# 四、知识抽取目标

对于每篇文献，尽可能完整地识别：

## Entity

医学或生物学知识实体，例如但不限于：

* Disease
* Phenotype
* Symptom
* Drug
* Compound
* Metabolite
* Gene
* Protein
* Pathway
* Cell
* Tissue
* Organ
* Biomarker
* Laboratory measurement
* Physiological process
* Biological process
* Treatment
* Intervention
* Procedure
* Diet
* Nutrient
* Food
* Exercise
* Behavior
* Lifestyle factor
* Environmental exposure
* Risk factor
* Population
* Clinical outcome

不要由于 entity 不属于预定义类别而丢弃有价值概念。

允许：

`entity_type = OTHER`

并同时保存模型给出的具体类型描述。

---

# 五、核心 Knowledge Assertion

逻辑上的核心知识可以表示为：

`(subject, relation, object, confidence, source_document)`

但是数据库内部不要只保存这个五元组。

每一个 assertion 至少应包含：

```text
subject_mention
subject_type

object_mention
object_type

detailed_relation
canonical_relation

llm_confidence

document_id
evidence_text

qualifiers

negated
speculative

extractor_version
prompt_version
model_name
created_at
```

其中：

## detailed_relation

必须尽可能忠实表达论文中的具体关系。

例如：

`significantly reduced fasting plasma glucose after 12 weeks of treatment`

不要为了图谱简洁而过早压缩信息。

## canonical_relation

用于知识图谱聚合和检索的简洁关系。

例如：

```text
increases
decreases
associated_with
increases_risk_of
decreases_risk_of
causes
prevents
treats
inhibits
activates
regulates
expressed_in
located_in
part_of
includes
interacts_with
correlated_with
predicts
biomarker_of
```

canonical relation 必须优先从一个统一维护的“关系概念候选池”中选择。

候选池必须配置化，不得硬编码在 Python 业务逻辑中。

如果没有合适候选：

```text
canonical_relation = OTHER
```

并保留 `detailed_relation`。

不得为了匹配候选关系而改变原文语义。

---

# 六、医学关系限定信息 Qualifiers

医学论文中的关系通常依赖上下文，因此需要额外保存 qualifier。

`qualifiers` 使用结构化 JSON。

根据文章内容，尽可能抽取例如：

```text
species
population
age
sex
disease_state
experimental_model

dose
route
frequency

duration
timepoint

measurement_method

direction
effect_size
statistical_significance

condition
tissue
cell_type

study_type
```

不存在的信息不要猜测。

例如：

```json
{
  "species": "mouse",
  "sex": "male",
  "dose": "50 mg/kg",
  "duration": "12 weeks",
  "statistical_significance": "p < 0.05"
}
```

---

# 七、Evidence 必须是一等数据

所有 assertion 必须能够追溯到原论文。

至少保存：

```text
document_id
evidence_text
```

如果输入格式允许获得位置，还应保存：

```text
section
paragraph
sentence
character_start
character_end
page
```

LLM 不允许生成论文中不存在的 evidence quote。

Evidence 的目的包括：

* 人工复核；
* 后续模型验证；
* assertion provenance；
* 处理知识冲突；
* 重新 canonicalization；
* 模型升级后重建知识库。

---

# 八、置信度

LLM 为每条 assertion 输出：

```text
llm_confidence: float
```

范围：

```text
0.0 <= confidence <= 1.0
```

该数值仅代表模型对“该论文是否支持这条抽取结果”的自评置信度。

不要将其解释为统计学意义上的真实概率。

未来数据库应允许额外加入：

```text
verification_score
supporting_document_count
contradicting_document_count
```

因此不要把 confidence 设计成不可扩展字段。

---

# 九、Entity Mention 与 Canonical Entity 必须分离

不要让每篇论文都重复要求 LLM 为一个医学概念生成大量同义词。

应采用：

```text
EntityMention
      ↓
CanonicalEntity
      ↓
EntityAliases
```

的架构。

## Extraction 阶段

只负责准确抽取论文实际出现的 entity mention。

例如：

```text
T2DM
```

或者：

```text
type 2 diabetes mellitus
```

## Canonicalization 阶段

跨文献判断不同 mention 是否属于同一个概念：

```text
T2DM
type II diabetes
type 2 diabetes
type 2 diabetes mellitus
        ↓
同一个 canonical entity
```

Canonical entity 至少包含：

```text
entity_id
canonical_name
entity_type
description
external_ids
```

Entity alias 单独存储：

```text
entity_id
alias
alias_source
confidence
```

未来允许接入：

* UMLS
* MeSH
* SNOMED CT
* ICD
* HGNC
* UniProt
* ChEBI
* DrugBank
* Gene Ontology

等医学/生物学 ontology 或 terminology。

但是第一版不能因为 ontology mapping 失败而丢弃实体。

外部 ontology mapping 应当是 enrichment，而不是 extraction 的硬依赖。

---

# 十、关系规范化

Relation normalization 与 extraction 分开进行。

Bronze 层保存：

```text
detailed_relation
```

Silver 层负责映射：

```text
detailed_relation
        ↓
canonical_relation
```

例如：

```text
"markedly increases the probability of developing"
"was associated with an elevated risk of"
"predisposes subjects to"
        ↓
increases_risk_of
```

同时必须永久保留原始 relation。

禁止覆盖原始抽取信息。

---

# 十一、推荐数据流水线

项目整体使用类似以下分层：

```text
Landing
│
│ 原始文献及 metadata
│
▼
Bronze
│
│ LLM 全文 extraction
│ raw entity mentions
│ raw assertions
│ evidence
│
▼
Silver
│
│ entity canonicalization
│ alias aggregation
│ relation canonicalization
│ normalization
│ deduplication
│
▼
Gold
│
│ canonical entities
│ canonical relations
│ assertions
│ provenance
│ database / parquet export
│
▼
Knowledge Base
```

各层的数据应尽可能能够独立保存。

禁止设计成只有“从头全部重新执行”才能恢复状态的 pipeline。

---

# 十二、数据库

默认使用：

**PostgreSQL**

作为主要可靠数据库。

第一版至少设计以下逻辑表：

```text
documents
processing_jobs

entity_mentions
entities
entity_aliases

raw_assertions
assertions

relation_types

extraction_runs
```

必要时可以增加辅助表。

## documents

保存文献 metadata、内容 hash 和处理状态。

## processing_jobs

保存每篇论文每一个 pipeline stage 的运行状态。

状态至少包括：

```text
PENDING
RUNNING
SUCCESS
FAILED
```

并保存：

```text
retry_count
started_at
finished_at
error_message
worker_id
```

## extraction_runs

记录：

```text
model
prompt_version
code_version
temperature
timestamp
```

从而保证未来能够区分不同版本抽出的知识。

---

# 十三、断点续传与幂等性

这是项目硬性要求。

系统必须支持：

```text
程序中断
服务器重启
API timeout
单文献处理失败
数据库异常
```

后重新执行，而不重复处理已经成功的论文。

每一篇文献必须拥有稳定的：

```text
document_id
content_hash
```

每次任务必须拥有稳定的 stage 标识。

写数据库必须尽可能使用：

* transaction；
* UNIQUE constraint；
* UPSERT；
* idempotent operation。

不得仅依赖内存变量判断任务是否已经完成。

当某篇论文失败时：

* 记录失败；
* 不影响其他论文；
* 可以单独 retry。

---

# 十四、并行处理

文献量级非常大，因此 extraction 必须支持并发。

优先使用简单可靠的 Python 并发模型，例如：

```text
asyncio
+
bounded semaphore
```

用于控制同时存在的 LLM API 请求数量。

需要配置：

```text
max_concurrency
requests_per_minute
tokens_per_minute
max_retries
request_timeout
retry_backoff
```

必须处理：

* rate limit；
* timeout；
* temporary API error；
* malformed structured output；
* connection error。

失败重试采用 exponential backoff + jitter。

不要无限重试。

不同文献之间应互相隔离。

---

# 十五、LLM API 抽象

所有模型调用通过统一 client，例如：

```text
LLMClient
```

业务代码禁止直接散落 OpenAI / Anthropic / Gemini 等 provider-specific API 调用。

至少提供：

```python
extract(...)
canonicalize(...)
```

等高层接口。

底层 provider 应可以替换。

优先要求模型返回 structured JSON。

对 LLM 返回数据必须进行 schema validation。

推荐使用 Pydantic model 定义输出。

当输出不符合 schema 时：

1. 尝试有限次数 repair / retry；
2. 若仍失败，则将该 document stage 标记 FAILED；
3. 保存原始 response 以便 debug。

# 十七、Prompt 管理

所有 LLM prompt 必须集中维护。

禁止将大段 prompt 散落在 Python 文件中。

建议：

```text
prompts/
    extraction.yaml
    relation_canonicalization.yaml
    entity_canonicalization.yaml
```

或者在项目保持简单的前提下统一为：

```text
prompts.yaml
```

每一个 prompt 必须具有明确版本，例如：

```text
extraction_v1
entity_canonicalization_v1
relation_canonicalization_v1
```

数据库中的 extraction run 必须记录 prompt version。

关系候选池同样放在配置文件中。

---

# 十八、LLM Extraction Prompt 的原则

Extraction prompt 必须强调：

1. 只提取论文实际支持的事实；
2. 不要使用模型自身医学知识补充论文；
3. 最大化 recall，但禁止 hallucination；
4. 区分 association 与 causation；
5. 区分 correlation 与 mechanism；
6. 正确处理否定；
7. 正确处理 speculative language；
8. 正确处理实验对象和人群限定；
9. 保存精确 evidence；
10. 不要把 Background 中引用他人工作的陈述误认为本文实验结果，但仍可作为“该论文陈述的知识”保存，并通过 qualifier 或 evidence 保留上下文；
11. 同一个 subject-object 可以存在多个不同 relation；
12. 不要因为两个实体在同一论文出现就自动建立关系。

# 二十三、数据质量检查

实现基本 quality checks：

* assertion subject 不得为空；
* assertion object 不得为空；
* detailed relation 不得为空；
* confidence 必须位于 `[0,1]`；
* evidence 必须来自对应 document；
* canonical relation 必须属于候选 pool 或 `OTHER`；
* entity ID 必须稳定；
* database foreign key 必须有效；
* 不允许出现明显重复 assertion。

Silver → Gold 之前执行 validation。

---

# 二十四、增量更新

系统必须允许未来新增论文：

```text
已有 1,000,000 篇
+
新增 10,000 篇
```

只处理新增或内容发生变化的文献。

不得要求完整重建知识库。

如果：

```text
prompt_version
model
canonicalization strategy
```

发生变化，应允许针对指定 stage 或指定文献重新运行。

原始 Bronze extraction 数据原则上不要因为 Silver 层算法升级而删除。

---

# 二十五、实体与关系的稳定 ID

不要直接使用 display name 作为数据库主键。

Canonical entity 使用稳定内部 ID，例如：

```text
ENT_xxx
```

relation type 同理。

Alias 修改不得导致 entity ID 改变。

如果之后成功映射到 UMLS / MeSH / HGNC / UniProt 等外部 ID，将其保存为 external identifier，而不是强制替换内部 ID。

# 二十六、最终实现原则

整个项目优先级按以下顺序：

```text
正确性
>
provenance
>
可恢复性
>
可维护性
>
吞吐量
>
代码炫技
```

不要一开始加入：

* Web UI；
* GraphRAG；
* chatbot；
* vector database；
* agent framework；
* 微服务；
* Kubernetes；
* 分布式消息队列。

除非实现核心 pipeline 确实需要。

第一版应该是一个可靠、容易理解的 Python knowledge extraction pipeline。
